# Архитектура RED//TRACE

## Границы первой версии

Приложение анализирует только локальный компьютер. Сетевой сервер, облачная синхронизация и удалённое управление по умолчанию отсутствуют.

```text
platform collectors -> parsers -> normalized events -> segment writer
                                                  -> indexes
indexes + query AST -> query executor -> local API -> web UI / CLI
```

## Компоненты

Архитектура разделена на два независимых контура: нативное ядро на Rust отвечает за сбор, нормализацию, индекс и поиск; UI отвечает только за представление и состояние рабочего места аналитика. Интерфейс можно заменить без миграции данных или изменения языка запросов.

### `model`

Нормализованное событие содержит обязательные timestamp, source, level и message, а также динамические поля. Имена вроде `event.id`, `process.name`, `user.name` сохраняют одинаковый смысл на разных ОС.

### `query`

Рукописный лексер и recursive-descent parser не требуют генератора грамматики. Текущий приоритет операторов: `NOT`, затем `AND`, затем `OR`.

### `storage`

Событие сначала подтверждается append-only WAL с checksum и `sync_data`. При достижении порога WAL атомарно преобразуется в неизменяемый JSONL-сегмент: временный файл синхронизируется, переименовывается, после чего атомарно обновляется `catalog.json`. WAL очищается только после публикации manifest. Для сегмента параллельно создаются отсортированные словари полей и терминов, а postings кодируются разностями document ID и varint. Все sidecar-файлы имеют собственные checksum.

При старте сегменты и остаток WAL объединяются по стабильному UID, повреждённый сегмент изолируется целиком. Повреждённый индекс регистрируется отдельно и не приводит к потере исходных событий. Compaction сначала публикует новый объединённый сегмент и manifest, затем удаляет старые файлы. Retention удаляет самые старые сегменты по времени создания и общему размеру базы.

### `index`

Первая вертикаль использует:

- `field -> value -> document IDs` для точных фильтров;
- `term -> document IDs` для текста;
- операции над упорядоченными множествами для булевых выражений.

Query executor читает словари и delta-varint postings непосредственно из нужных сегментов. Версионируемый offsets sidecar позволяет читать совпавшие JSONL-записи через прямой `seek`, не сканируя весь сегмент. В памяти остаются индекс активного WAL и ограниченный кэш четырёх сегментных индексов; полная историческая база больше не восстанавливается в RAM при старте. API и AST при этом не меняются.

### `ingest` (удалённые агенты)

Опциональный контур приёма событий с других машин. Включается только
переменной окружения `REDTRACE_INGEST_BIND` и слушает отдельный порт, не
связанный с localhost API. Аутентификация — постоянный токен агента;
в реестре `agents.json` хранится только SHA-256-хэш токена, сравнение —
за постоянное время. Управление токенами идёт через localhost API
(`POST/GET/DELETE /api/agents`) под тем же session-token middleware, что и
остальные эндпоинты.

Запрос агента ограничен 1000 событий и 8 МБ, события проходят строгую
валидацию (RFC3339-timestamp, безопасный алфавит source, лимиты полей) и
нормализуются заново: UID вычисляется в области агента, поля `agent.id`,
`agent.name`, `host.name` проставляются сервером, зарезервированные ключи
(включая `collector.cursor`) отбрасываются — курсоры чужих машин не могут
попасть в локальные checkpoints. Дальше события входят в общий bounded-канал
ingestion, дедуплицируются по UID и обрабатываются детект-движком как
локальные.

### `agent`

Легковесный бинарник `redtrace-agent` без собственных зависимостей сбора:
он переиспользует платформенные коллекторы ядра и их durable checkpoints из
своего state-каталога. Доставка — at-least-once: локальный checkpoint
агента продвигается только после подтверждения батча сервером, при
недоступности сервера события копятся в bounded-очереди (20 000 событий).
Удалённый транспорт использует HTTPS/rustls с проверкой цепочки сертификата и имени сервера. HTTP-клиент поверх `std::net::TcpStream` оставлен только для loopback. Non-loopback listener требует PEM certificate/key. Сервер отвечает 200 только после регистрации UID в durable-наборе после WAL sync. 401 завершает агента; 400/413 разделяют батч до одиночного события, которое сохраняется в bounded quarantine перед продвижением checkpoint. Таймауты и 5xx вызывают повтор с backoff.
Heartbeat каждые 30 секунд обновляет last_seen агента на сервере.

### `audit::windows`

Модуль описывает действия как данные: цель, ожидаемые Event ID, точная команда и стратегия отката. HTTP API возвращает только preview. В Windows desktop доступен opt-in dev-helper через Tauri IPC: UAC, взаимная проверка PID/path, protected snapshot, selected-only apply/verify/rollback. Отдельные запросы выполняют pinned-artifact Sysmon install/removal и current-user read-only channel grants/restores. Frozen binary bytes передаются по IPC; elevated helper не открывает source filepath от caller. Production требует подписанной поставки.

### `detection`

Движок получает только события, уже подтверждённые в WAL. Окна корреляции ограничены по времени и числу событий, повторные threshold-срабатывания подавляются на заданный срок. Алерт содержит severity, confidence, risk score, MITRE ATT&CK, ключ группировки и UID событий-доказательств. Перед публикацией в UI алерт записывается в отдельный JSONL-журнал с checksum и `sync_data`; повреждённые строки изолируются при восстановлении.

### `app/events`

Фронтенд использует узкую границу данных: `types.ts` описывает нормализованное событие, а `api.ts` инкапсулирует localhost API и преобразование ответа. Экран не знает формат транспортного JSON и может позже перейти с HTTP на Tauri IPC без переделки панелей.

В desktop-сборке Tauri генерирует случайный сессионный токен, передаёт его Rust-sidecar через окружение и предоставляет встроенному UI только через Tauri command. Все API-запросы используют `x-redtrace-token`; сравнение выполняется за постоянное число итераций. Без токена localhost API отвечает `401`. В режиме разработки без переменной токена API сохраняет совместимость с отдельным локальным UI.

### `desktop`

Статический Vite bundle переиспользует тот же React workspace без серверного Node.js. Tauri/Wry управляет одним окном, single-instance и жизненным циклом sidecar. Сборочный скрипт создаёт target-specific имя бинарника для macOS, Windows и Linux. CSP разрешает сетевое соединение только с `127.0.0.1:9710`.

Рабочее место разделено на поток событий и алерты. События строятся вокруг одного состояния выбранного события и четырёх независимых представлений:

```text
запрос + диапазон времени
          |
          v
поля -> поток событий -> подробности
             |
             v
       гистограмма времени
```

На широком экране поля, поток и подробности видны одновременно. На компактном экране поток остаётся основным контекстом, а поля и подробности открываются как боковые панели с затемнением фона. Это сохраняет одну информационную архитектуру на Windows, Linux и macOS.

## Визуальная система

- шаг компоновки 4/8 px, высота основных контролов 34 px;
- нейтральные почти чёрные поверхности и один бирюзовый акцент для выбора и живого состояния;
- красный и янтарный зарезервированы для риска, а не для декора;
- моноширинный шрифт используется только для времени, идентификаторов, запросов и сырых данных;
- плотность рассчитана на длительную работу: строка события 58–62 px, подробности раскрываются отдельно;
- адаптивный порог 820 px переводит вспомогательные панели в drawers без потери функций.

## План сегментного хранилища

```text
data/
  catalog.json
  active.wal
  segments/
    00000001/
      meta.bin
      events.zst
      fields.dict
      fields.postings
      terms.dict
      terms.postings
      timestamps.bin
```

Закрытые сегменты неизменяемы. По времени в метаданных хранится min/max, поэтому нерелевантные сегменты пропускаются до чтения. Удаление по retention удаляет целые сегменты.

## Целевые бюджеты

- idle RSS до 50 МБ;
- активный сбор до 100 МБ;
- отсутствие фонового полного сканирования;
- жёсткий лимит диска и retention;
- запуск UI и API менее чем за две секунды в release-сборке.

## Текущий этап

Сейчас готов кроссплатформенный вертикальный прототип: собственный DSL, дисковый поиск по postings, localhost API, read-only сбор macOS Unified Log, Linux journald и Windows Security/PowerShell/Sysmon, bounded-очередь ingestion с backpressure, WAL и неизменяемые сегменты с восстановлением после перезапуска. Добавлен bounded-движок базовых детектов и сохраняемый журнал алертов. Рабочий контур не подставляет демонстрационные события. UI поддерживает live-обновление, адаптивные и изменяемые по ширине панели, поток событий, серверную гистограмму, отдельный alerts workspace и обязательный процессный контекст (`event.description`, `process.command_line`, `process.pid`, `process.parent.pid`). Метрики очереди, WAL, сегментов, алертов и ошибок отдаются в `/api/health`.

До production-ready MVP остаются четыре инженерных блока:

1. Довести коллекторы до production: Endpoint Security на macOS, auditd/netlink и cursor на Linux, Event Log subscription/bookmark на Windows.
2. Добавить offsets для прямого чтения выбранных событий, memory mapping и полные миграции формата.
3. Диагностика, безопасный экспорт, виртуализация длинного потока и расширяемые пользовательские правила без выполнения кода.
4. Подписание/notarization установщиков и отдельный privileged helper для фактического apply/verify/rollback Windows Audit.
